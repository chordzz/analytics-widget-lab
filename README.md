# analytics-widgets-lab

Sandbox for building the Analytics frontend ahead of the real repository, so the data structures and configurations are settled before the migration lands. Plan: [`../Analytics_Frontend_Plan.md`](../Analytics_Frontend_Plan.md). Requirements: the Analytics FRD.

> **New here? Read [`ENGINEERING.md`](ENGINEERING.md) first.** This file is the
> phase-by-phase record of the requirements work. `ENGINEERING.md` is the
> orientation: how the repository is arranged, why it contains two applications,
> and what wiring a backend actually involves.

Standalone Vite + React + TypeScript + Tailwind 4. Not a consumer of `@SMCDAO/ui` — styling goes through CSS custom properties in `src/index.css` so the whole surface can be re-skinned against the real design system later.

## Commands

```bash
bun install
bun dev              # the eligibility explorer
bun test             # 437 tests
bun run typecheck
bun run docs         # regenerate the contract documentation
```

`bun run build` needs Node 20.19+ or 22.12+ (Vite 8's `engines`). On the Node v16 default it dies on a `node:util.styleText` mismatch, which is the environment and not the code. Either of these works: `bunx --bun vite build`, or `nvm use 22.23.0 && bun run build`. `bun test` and `bun run typecheck` run on Bun and are unaffected.

## Contract documentation

Generated by `bun run docs` from the code that implements it. `src/contract-docs/render.test.ts`
fails if they drift, so they cannot go stale silently.

| File | Nature |
|---|---|
| [`docs/PUBLICATION_CONTRACT.md`](docs/PUBLICATION_CONTRACT.md) | **Enforceable** — what a Source System must declare. The backend validates against this. |
| [`docs/DATA_SHAPES.md`](docs/DATA_SHAPES.md) | **Guidance** — what each Visualization Family requires. Not a publication gate. |
| [`docs/DIVERGENCES.md`](docs/DIVERGENCES.md) | **The divergence register** — every place this implementation does not match the FRD, with the clause, the reason, and how long it is meant to last. |
| [`docs/WIDGET_DATA_CONTRACT.md`](docs/WIDGET_DATA_CONTRACT.md) | **For the backend team** — what each widget asks for, per Type: required Field roles, the `DatasetQuery` sent, the response shape. |
| [`docs/WIDGET_DATA_CONTRACT.pdf`](docs/WIDGET_DATA_CONTRACT.pdf) | The same document, laid out for sending and printing. `python3 scripts/widget-contract-pdf.py` after `bun run docs`. |
| [`docs/analytics-contract.json`](docs/analytics-contract.json) | Machine-readable form of both. |

The division is deliberate: the backend enforces **completeness of declaration**, the frontend derives
**visualization eligibility**. A Dataset is published to describe data, not to satisfy a chart — one
that satisfies zero Visualization Families today is still valid and still publishes.
`src/domain/publication-contract.ts` is the executable version of the enforceable half; the backend
can mirror its rules directly.

## What Phase 2 establishes

**Six states that cannot be confused.** `resolveRenderState` is a pure function with its own tests,
and `WidgetFrame` gives each state its own colour, icon and wording. A denial is not an empty chart
(which would read as zero) and not an error (which would read as broken). A withdrawn Dataset shows
nothing rather than last-known figures.

**Per-Widget independence.** Each Widget owns its retrieval and its error boundary. In the runtime
demo you can hold five different states on one board at once — two Widgets denied, two withdrawn, one
empty — while the rest keep working. That is FR-DA-10 shown rather than asserted.

**Read-only by construction.** `RendererProps` contains no callback, no port and no dispatch, so a
renderer has nothing it *could* call to write. FR-VZ-08 is enforced by the type rather than by
reviewer vigilance, and a test asserts the props the runtime actually passes contain no functions.

**Aggregation belongs to the query.** A Widget asks for "sum of settlement_value by corridor" and
receives aggregated rows. No renderer ever reduces raw records — that would let each Widget decide
what "sum" means, which is the divergent-definition failure the capability exists to prevent, and it
would ship records a Viewer may not be entitled to.

**Classification and renderers are separate.** All 42 Visualization Types are classified; 13 are
built. A Type that is eligible but unbuilt says so plainly, and says the Dataset is fine — a
configuration gap, not a data state.

## What Phase 3 establishes

**The Catalogue cannot retrieve data.** FR-DP-11 requires discovery without retrieval, so browsing
and retrieval are separate ports and `CataloguePort` exposes nothing that returns rows. A test asserts
the port's surface, making the property structural rather than a matter of discipline.

**Authorization is checked twice, deliberately.** The Catalogue hides Datasets a Viewer may not
consume (FR-DP-12) *and* retrieval denies them (FR-DA-09). The duplication is the point: a
Catalogue-only check would leave a Widget bound before access was revoked still serving data, which
FR-DA-12 forbids.

**Publishing and Scope are separate gates.** A published Dashboard scoped Personal stays private.
Both must pass — see Finding 9.

**One composition root.** Every fake is constructed in `composition-root.tsx` and injected through
context. No other module imports one, so swapping in real adapters is a one-file change.

## Walking UC-02

`bun dev`, Authoring tab, as the Operations lead:

1. **Discover** — five Datasets, descriptions only. Switch to Finance analyst and it drops to three.
2. **Bind** — pick Peniremit settlements. Correlation reads *"Not offered — at least 2 Measures"*,
   exactly as UC-02 describes. Types classified but not yet built are visibly disabled.
3. **Map** — slots accept only Fields of the right role; a default mapping is proposed.
4. **Expose** — only Fields the publisher declared filterable can be offered to Viewers.
5. **Review and publish** — the preview is the real runtime. Choose a Scope, save as a draft, publish.

Then switch Viewer. At Personal Scope the Dashboard vanishes; at Organization-wide it appears with the
Peniremit Widget denied and everything else working.

## What Phase 4 establishes

**Cross-Source-System composition is unremarkable.** Nothing in the model relates two Widgets bound
to Datasets from different Source Systems; their only shared context is the Dashboard. The absence of
special handling is the feature (FR-CO-03).

**A Control declares how it corresponds, never which Widgets it holds.** Correspondence is computed
per Widget, so adding a Widget to a Dashboard brings it under an existing Control with no
reconfiguration — and removes a whole class of stale-configuration bug.

**"Leave other Widgets unaffected" is shown, not just honoured.** The Control reports *"Affects 2 of
3 Widgets — Corridor coverage declares no time dimension"*. A Control that silently moved two of three
Widgets would leave a Viewer guessing whether the third was stale, filtered differently, or broken.

**A Control cannot overrule the publisher.** If a Field is not declared filterable (FR-DP-05), no
Dashboard Control can filter on it.

## Walking UC-03

Author a second Widget on the Payroll Dataset — a different Source System — and it joins the same
Dashboard. Add a third on Corridor coverage, which has no Time Dimension. Then **Edit layout → Add
date-range Control**. Changing the range narrows both trend Widgets to their own Dataset's Time
Dimension (`settled_at` and `disbursed_on` — never a shared field name) and leaves the third
untouched, saying why.

Naming follows the Analytics Ubiquitous Language exactly — Dataset, Field, Dimension, Measure, Time Dimension, Visualization Type, Visualization Family, Data Shape, Catalogue. No synonyms; the term *Department* is avoided entirely (§8 records it as ambiguous).

## What Phase 1 establishes

**Eligibility is computed, never stored.** Per the invariant, a Dataset is not bound to any Visualization Type — any Family whose Data Shape it satisfies may present it. `offeredVisualizationTypes(dataset)` is the FR-VZ-05 decision; nothing persists a binding.

**Three outcomes, not two.** `satisfied` / `unsatisfied` / `indeterminate`. The third is the honest modelling of Finding 1: five Families declare Data Shapes referencing properties the publication model cannot express, so the system genuinely cannot decide. Those Types are withheld — FR-VZ-05 says offer only what the Dataset is *known* to satisfy — and the UI explains why rather than silently dropping them.

**Exclusions are explained.** Every non-satisfied outcome carries a reason, so the authoring surface can tell an Author why a Visualization Type isn't on offer (UC-02).

## Demonstrating Finding 1

`bun dev`, then toggle **Apply proposed Field semantics**. For the Peniremit settlements Dataset:

| | Families satisfied | Types offered | Undeterminable |
|---|---|---|---|
| Published model as the FRD defines it today | 9 / 13 | 30 | 3 |
| With the proposed Field-semantic extension | 11 / 13 | 37 | 0 |

Seven additional Visualization Types become available for a single Dataset. The extension is not a blanket unlock: Geospatial still resolves to *not satisfied* for that Dataset because it has no location Field, and Composition stays unsatisfied for the Active users Dataset because distinct users are not summable across products.

## Fixtures

Chosen to span the predicate's range and to reproduce the use cases verbatim:

- **Peniremit settlements** — UC-02 exactly: a Time Dimension, a corridor Dimension, and deliberately only one Measure, so Correlation must not be offered. If a scatter plot ever appears for this Dataset, FR-VZ-05 is broken.
- **Payroll disbursements** — UC-03's partner; two Measures, so Correlation *is* eligible. Carries personal data (FR-DA-14).
- **Active users** — the §2.1 divergent-definition story; a Measure that looks summable but isn't.
- **Corridor coverage** — no Time Dimension, so Trend/Temporal/Chronological are definitively unsatisfied; carries a geographic Field.
- **Journal entries** — no Measure at all; carries a state Dimension, the Status Family's second route.
